# Запуск и эксплуатация OT Center

## Локально

Требуется Node 24.15+ (проверено 24.16.0), npm 11.13.0. Не удалять lockfile.

```sh
npm ci
npm run db:migrate
npm run dev
```

Скопируйте `.env.example` в `.env`, задайте `BETTER_AUTH_URL` равным локальному origin и случайный `BETTER_AUTH_SECRET` (минимум 32 символа). Не сохраняйте секреты в Git. Для разработки без почтового транспорта регистрация ставит письмо в приватную очередь; это не сообщение об успешной внешней доставке. Кабинет требует подтверждение почты.

```sh
npm run lint
npm run typecheck
npm test
npm run build
npm run test:seo
npm run test:e2e
```

Конкретные результаты и ограничения этих команд записаны в `IMPLEMENTATION_STATUS.md`; наличие команды само не означает passed.

## Бесплатное serverless окружение

1. Подключить существующий/отдельный бесплатный libSQL аккаунт самостоятельно, сохранить `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN` в server secrets окружения. Не включать платные overages. Штатные миграции не содержат персональных данных.
2. Указать auth URL, секрет, canonical host. Для staging задать `OT_APP_ENV=staging`, `OT_NOINDEX=true`; ограничить доступ preview средствами хостинга. Для production не включать sandbox.
3. Явно применить миграции к выбранной БД: `npm run db:migrate -- --remote`. Сначала проверить URL/окружение и создать backup существующих данных. Cold start не запускает remote migrations.
4. `npm run build:vercel` создаёт локальный deployment artifact без публикации. В этой задаче владелец уже отдельно разрешил production-деплой после проверок. Перед выпуском проверить постоянную БД, миграции, auth и приём заявок; разрешение на публикацию не заменяет готовность этих зависимостей. Для будущих выпусков требуется соответствующее поручение владельца.
5. Заполнить SMTP/CRM только после подключения сервисов. `OT_EMAIL_DELIVERY_ENABLED` отвечает за transactional auth mail, `OT_CRM_DELIVERY_ENABLED` за заявки. Массовая рассылка отсутствует; приглашения создают одноразовую ссылку для уполномоченного менеджера, данные группы не рассылаются автоматически.

`vercel.json` содержит одну ежедневную cron, без платной поминутной частоты. Нужен длинный случайный `CRON_SECRET`. `GET /api/v1/operations/tick` требует bearer secret; администратор с MFA может вручную запустить небольшой batch через `/api/v1/admin/operations/tick`. При сбое запись остаётся durable, backoff до 1 h, после восьми попыток — failed. Админка показывает очередь и основание retry. Секреты/текст verification mail не возвращаются в обзоре очереди.

Вызов ограничивает порции просроченных попыток, напоминаний, очереди и инцидентов; постоянного worker и поминутного мониторинга нет. Напоминания создаются в кабинете или организации по явно выбранной календарной дате/часовому поясу и максимум трём смещениям. Срок доступа берётся из действительного назначения; дату повторного обучения выбирают явно, она не объявляет срок действия документа. По умолчанию доставка только внутри кабинета. Поздние окна отмечаются пропущенными, без массовой досылки. Отказ слушателя и отзыв членства проверяются ещё раз перед доставкой. Подробности: [ORGANIZATION_REPORT_AND_REMINDERS.md](ORGANIZATION_REPORT_AND_REMINDERS.md).

## Программы, доступ и документы

Зарегистрировать и подтвердить email первого администратора. `npm run admin:bootstrap -- --bootstrap --email <email> --reason <основание>` назначает только первого администратора, без известного пароля. Настроить TOTP в кабинете. Дальнейшие роли управляются через защищённый API и журнал.

Редактор создаёт draft версии: RU/KK, аудитория, материалы, обязательные действия, вопросы/варианты/правильные ответы, длительность/порог/пересдачи. Затем review и публикация другим reviewer. Ключи вопросов не выдаются учащемуся. Новая публикация не меняет существующее обучение. Практика отмечается инструктором с evidence.

Для документов загрузить PDF AcroForm с полями `learnerName`, `programTitle`, `serial`, `issuedAt`, `verificationUrl`, `issuerName` (или отобразить фактические имена через fieldMap), Unicode TTF/OTF с правом использования и при необходимости координаты QR. Шаблон <=1 MB, не содержит JavaScript/actions/embedded files; второй reviewer утверждает его. PDF не появляется до фактической eligibility и успешной render job. Сбой шрифта/поля оставляет pending и конкретный код в outbox.

После реальной ошибки render создать новый исправленный шаблон той же программы и с тем же issuerName, передать другому reviewer на утверждение. Issuer/admin с MFA вызывает `POST /api/v1/admin/credentials/{id}/repair` с `{templateId,reason}`; основание от 10 до 2000 символов. Активная lease требует дождаться завершения worker. Операция атомарно привязывает pending к новому шаблону, оставляет прежний номер и ссылку проверки, возвращает существующую durable job в очередь и фиксирует основание в аудите. Затем разрешённый worker повторяет генерацию. Уже выданные и отозванные документы не меняются; для них применяется отдельная процедура отзыва/замены. Изменять записи SQL вручную для обхода этих ограничений нельзя.

Администратор с MFA может остановить новые зачисления на опубликованную версию с основанием. Старая версия и её история остаются неизменяемыми; прежние назначения и подтверждение ранее оформленных счетов продолжают действовать. Повтор прежнего idempotent запроса возвращает прежнюю запись, но новые заказы/счета/назначения запрещены до возобновления. См. [PROGRAM-INTAKE.md](PROGRAM-INTAKE.md).

`/admin/document-batches` позволяет issuer/admin проверить до 10 записей перед оформлением или отзывом. Первое подтверждение доступно 15 минут. Каждая запись выполняется атомарно вместе со своим результатом; повтор не выпускает второй документ. Изменившийся бланк/состояние требует нового просмотра. Оформление регистрирует pending и ставит подготовку PDF в очередь. Частичный результат явно показывает отклонённые записи. После инфраструктурной ошибки обработку можно продолжить с прежней группой; незавершённая lease ограничивает параллельный запуск.

`/admin/support` доступен администратору с MFA. Заметки поддержки и уточнения добавляются с автором/датой; исходная запись сохраняется. Не записывать пароли, банковские данные и лишние персональные сведения. Содержание заметок не дублируется в техническом аудите.

## Backup, restore, rollback

Задайте `OT_BACKUP_PASSWORD` (случайная строка не короче 24 символов, хранить отдельно от backup).

```sh
npm run db:backup -- backup artifacts/backup-unique.otb
npm run db:backup -- restore artifacts/backup-unique.otb .data/restore-unique.sqlite
```

Backup читает согласованный snapshot транзакцией, содержит таблицы/файлы/связи и шифруется AES-256-GCM со scrypt. Команда не перезаписывает существующий файл. Restore допускает только новый пустой локальный target, проверяет foreign keys, не меняет remote DB. Отдельно проверить права, число документов, sha256 и ссылки в восстановленной изолированной копии. Время drill указывать фактическое; RPO/RTO инфраструктуры не заявлены без измерения.

Миграции additive и с checksum. Уже применённый SQL не редактировать: добавить следующий номер. Для отката сначала выключить новые записи/внешние операции, сохранить backup и вернуть совместимый предыдущий серверный artifact. Не удалять результаты, заказы или документы для отката. Возврат на старый демонстрационный frontend недопустим как способ обслуживать реальных учеников; старый public-only artifact можно использовать только с закрытыми новыми API. Публичный DNS/host в этой работе не переключается.

После подключения и миграции разрешённой remote БД обязательно запустить `node --env-file-if-exists=.env --import tsx scripts/db-readiness.ts --remote --probe-foreign-keys`. Три свежих клиента проверяют `PRAGMA foreign_keys=1`, миграции и существующие FK; заведомо неверная тестовая ссылка должна быть отклонена, транзакция всегда откатывается. Сервис и migration CLI отказывают в работе при отключённых FK. Один `PRAGMA foreign_keys=ON` во время миграции не считается подтверждением новых HTTP connections. Фактический remote probe и production rollback пока `not_run`; локальные проверки не заменяют эти release gates.

## Инциденты и квоты

`/admin/incidents` показывает события по текущей роли: администратор — все, issuer — документы, finance — платежные события. Порог ожидания задаётся `OT_ALERT_OUTBOX_MINUTES` (60), `OT_ALERT_LEAD_MINUTES` (120), `OT_ALERT_CREDENTIAL_MINUTES` (60), `OT_ALERT_PAYMENT_MINUTES` (1440). Это пороги операционного наблюдения, не обещание реакции или нормативные сроки. Сканы чередуют источники и ранее не просмотренные записи, чтобы длинная очередь не скрывала новые ошибки. Принятие в работу и закрытие требуют основания. Пока причина активна, закрытие запрещено; исправленные источники закрываются автоматически при следующей проверке. Отклонённое sandbox событие можно закрыть после проверки и пяти минут без повторения.

Уведомления сотрудникам в кабинете создаются один раз на цикл события. `OT_OPERATIONAL_ALERTS_ENABLED=0` отключает внешнюю отправку. Если владелец отдельно согласовал канал, для включения нужны SMTP_URL, MAIL_FROM, один OT_ALERT_EMAIL и флаг 1. Ошибка доставки остаётся в очереди; запись там не означает доставленного email. Устаревший/закрытый цикл отменяется. Невозможность записать счётчик не превращает успешную доставку в повтор. Не включать внешний канал в рамках текущего разрешения на production без согласования отправки.

- CRM pending/failed: проверить настройки/доступность, сохранённый external lead ID, повторить job с основанием. Notes retry не создаёт новый lead. Корреляционный marker позволяет искать неопределённый create, однако внешняя система не предоставляет общей транзакции с нашей БД — uncertain remote create требует наблюдения и сверки.
- Экзамен: deadline и итог читаются с сервера. 409 означает конфликт revision; перезагрузить сохранённый ответ, не отправлять stale данные молча.
- Оплата: redirect/query не подтверждают состояние. Sandbox webhook проверяется подписью, merchant, суммой, валютой. Реального адаптера пока нет.
- Документ pending: исправить проверенный шаблон/шрифт новой версией или повторить разрешённую render job; номер не менять вручную.
- `/api/health` проверяет процесс, `/api/ready` — доступность схемы. Внешний мониторинг/alert канал на настоящем аккаунте не настроен автоматически. Превышение free quota — отказ сервиса, не скрытый переход к paid тарифу.

Не логировать PII, токены, ответы экзамена и payload внешних провайдеров. Диагностика связывается по requestId и внутренним entity IDs. Реальная доступность региона хранения/почты/платежного сервиса подтверждается при подключении владельцем; юридическое лицо и разрешения центра повторно не проверяются.
