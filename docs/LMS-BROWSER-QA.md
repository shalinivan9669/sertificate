# Проверка LMS в настоящем браузере

Сценарии используют Chromium и работающий сервер приложения. Они не подменяют ответы auth, экзамена, оплаты или выдачи документов. Прерывание запроса прогресса используется только для проверки ошибки сети и повторного сохранения.

Контактный сценарий перехватывал ответы запросов в браузере. Он проверяет интерфейс и обработку состояний; реальная заявка в CRM не отправлялась, доставка в amoCRM этим запуском не подтверждается. В LMS-сценариях серверное выставление и подтверждение синтетического корпоративного счёта, результаты экзамена и проверки доступа выполнялись настоящими API тестового сервера.

По результатам браузерной проверки исправлены два поведения приложения: обновление списка версий больше не размонтирует редактор и не стирает сообщения сохранения, передачи на проверку и публикации; ответ 429 при входе теперь сообщает об ограничении запросов. Сохранность сообщений редактора проверена финальным обычным staff-сценарием. Старый `admin-diagnostic-report.json` сохраняет отметку о дефекте прежней сборки и не заменяет финальный `admin-report.json`.

Отдельно исправлены ожидания тестов: сценарий слушателя дожидается загрузки выбора вариантов или кнопки записи перед выбором точного `fixture.versionId`; staff-сценарий проверяет именно путь перехода после входа и соблюдает `Retry-After` перед повтором при 429. Ограничения входа на сервере не отключались и не ослаблялись.

Все данные сценариев синтетические. Запускайте сервер только с отдельной локальной `.data/e2e.sqlite`, не подключайте production или удалённую БД. Создание fixtures запрещено при `VERCEL` или `TURSO_DATABASE_URL`, а также без явного тестового окружения. Не используйте эти тестовые записи, PDF и подтверждения счетов как реальные учебные результаты или финансовые документы.

В PowerShell, из корня репозитория:

```powershell
$env:NODE_ENV = 'test'
$env:OT_ALLOW_TEST_SEED = '1'
$env:OT_DATABASE_PATH = Join-Path (Get-Location).Path '.data/e2e.sqlite'
$env:TEST_BASE_URL = 'http://127.0.0.1:3101'
npx tsx tests/e2e-fixtures.ts
```

Работающий тестовый сервер должен использовать тот же `OT_DATABASE_PATH`, `BETTER_AUTH_URL`, совпадающий с `TEST_BASE_URL`, и постоянный `BETTER_AUTH_SECRET` достаточной длины. Полные инструкции сборки и окружения находятся в [RUNBOOK.md](RUNBOOK.md). Не запускайте второй сервер на уже занятом порту. Для окончательной проверки используйте собранное приложение; при изменении исходников обновите сборку до следующего запуска.

```powershell
node tests/lms-browser.mjs
node tests/lms-auth-browser.mjs
node tests/lms-admin-browser.mjs
```

`BROWSER_PATH` позволяет указать установленный Chromium. По умолчанию используется локальный Google Chrome для Windows.

| Сценарий | Что проверяет |
| --- | --- |
| `lms-browser.mjs` | RU/KK и адаптивные экраны; сохранность исторических направлений; HTTP 404; вход и возврат к программе; ошибка сети, сохранение и восстановление прогресса; фиксированное время попытки; автосохранение и конфликт двух вкладок; серверные pass/fail; чужие идентификаторы; бессилие поддельных cookies; выход |
| `lms-auth-browser.mjs` | Регистрацию, настоящий токен подтверждения из локальной очереди, подтверждение email, настройку TOTP через UI, следующий вход с MFA, восстановление пароля через настоящий токен очереди |
| `lms-admin-browser.mjs` | Настоящую настройку MFA для каждого сотрудника; права ролей; справочник источника без выдуманного курса; визуальный редактор; независимую публикацию и запрет утверждения автором; организацию, приглашение и CSV с предпросмотром; назначения и отчёт; настройки счетов; приватный PDF и независимое утверждение шаблона |

Для полного браузерного сценария корпоративного счёта тестовому серверу нужны `OT_INVOICE_ENABLED=1` и `OT_INVOICE_ISSUER_JSON`, соответствующий схеме из [CORE_INVOICES.md](CORE_INVOICES.md). В изолированном тесте используются только явно помеченные `TEST ONLY` сведения. Сценарий создаёт организационный счёт на двух сотрудников, проверяет единую общую цену и запрет индивидуального оформления, затем подтверждает синтетическое поступление через форму финансового сотрудника. Банковский перевод и обращение к платёжному провайдеру не выполняются. Если счета отключены, тест проверяет только видимое отключённое состояние; результат этой ветки не подтверждает сценарий выставления и сверки счёта.

Перед повтором сценария слушателя его прежняя попытка должна быть очищена только в изолированной БД:

```powershell
npx tsx tests/e2e-reset-learning.ts
node tests/lms-browser.mjs
```

Очистка ограничена исходным `fixture.versionId` двух известных пользователей `@example.test`, проверяет точный путь к fixture-БД и отказывается удалять записи, связанные с документами. Назначения других версий, корпоративные счета, связанные финансовые записи и журнал аудита сохраняются. Не запускайте очистку одновременно с другими тестами или проверкой текущих попыток.

Результаты сохраняются в `artifacts/lms-browser/report.json`, `auth-report.json` и `admin-report.json`; рядом находятся снимки экранов. Список фактически выполненных проверок ведётся в `IMPLEMENTATION_STATUS.md`. Наличие сценария в репозитории само по себе не означает успешный запуск.
