# Изолированная проверка старого LMS после расширения схемы

Проверка 7 сентября 2026 года завершилась: **15 операций passed, 0 failures, exit 0**. Сохранённый старый LMS действительно запущен на новой синтетической копии БД со схемой `001–009`; его защищённые HTTP GET сохранили существующий сеанс, пользователя, курс и прогресс. **Возвращать этот artifact в production как приложение с доступом на запись нельзя**: он не реализует новые ограничения набора, напоминания, инциденты и пакетную обработку документов.

Это локальная проверка совместимости данных и проверенного отказа от небезопасного отката для B53/T083. Она не подтверждает production rollback, удалённый restore, RTO/RPO или работу старого приложения с новыми бизнес-правилами. Для работающей системы нужен artifact, который поддерживает все активные правила текущей схемы, либо исправление вперёд. Снимать запрет набора или удалять новые данные ради запуска старого приложения нельзя.

## Проверенные версии и доказательства

- Старый artifact: build ID `6aa9fbb6-2c27-4ec9-bb12-8eb4f4fd60f9`.
- Fingerprint 95 принадлежащих приложению серверных `.mjs` и `package.json`: `bb111d849aceac33f5e46fe6773987624b0c533a8b0217927699772aa7aac979`. Хэш не включает бинарные зависимости и не заменяет подпись/проверку происхождения релиза.
- Успешный отчёт: `artifacts/rollback/report-2026-09-07T15-44-09-935Z.json`, начало `2026-09-07T15:44:00.834Z`. Артефакты и частные тестовые БД исключены из Git.
- Фактически применены `001-core.sql`, `002-business.sql`, `003-credential-templates.sql`, `004-corporate-invoices.sql`, `005-invoice-allocations.sql`, `006-operational-incidents.sql`, `007-learning-reminders.sql`, `008-program-intake.sql`, `009-staff-workflows.sql`.
- Исходная синтетическая БД создана текущими сервисами сразу на схеме `001–009`. Затем экспортирована, восстановлена в новый файл и проверена повторным применением тех же миграций: 43 таблицы, 49 строк, точное сохранение. Этот прогон не является отдельным тестом перехода заполненной БД со схемы `005` на `009`.

Текущий HTTP auth handler выполнил настоящий вход заранее подтверждённого синтетического слушателя. Сеанс перенесён вместе с копией БД; старому приложению не выполняли новый вход и не создавали учебные записи через его API.

## Отказ до запуска несовместимого приложения

Каждый сценарий использовал свою новую копию синтетической БД. Во всех восьми случаях preflight вернул `applicationRollbackAllowed: false`, `isolatedReadDiagnosticAllowed: false`; старый сервер **не запускался**:

| Состояние отдельной копии | Проверенный код отказа |
| --- | --- |
| Закрыт набор на существующую опубликованную версию | `CLOSED_INTAKE_UNSUPPORTED` |
| Ожидает доставка `operations.alert` | `UNSUPPORTED_OUTBOX_WORK` |
| Ожидает доставка `learning.reminder` | `UNSUPPORTED_OUTBOX_WORK` |
| Активное напоминание и запланированная доставка | `ACTIVE_REMINDERS_UNSUPPORTED` |
| Открытый операционный инцидент | `ACTIVE_INCIDENTS_UNSUPPORTED` |
| Пакет документов в preview с ожидающим элементом | `UNFINISHED_CREDENTIAL_BATCHES` |
| Неизвестная миграция `010` | `UNKNOWN_DATABASE_MIGRATION` |
| Несовпадение checksum миграции `008` | `MIGRATION_CHECKSUM_MISMATCH` |

Preflight дополнительно учитывает незавершённые/повторяемые доставки, частичные пакеты, ожидающие/ошибочные элементы, целостность SQLite и внешних ключей, отсутствующие таблицы и расхождение ledger. Не все дополнительные ветви были отдельными сценариями этого прогона.

Даже на копии без активных ограничений preflight возвращает `applicationRollbackAllowed: false` и `TARGET_LACKS_REQUIRED_FEATURE_CAPABILITIES` для четырёх расширений `006–009`; только изолированный GET diagnostic разрешён. В коде нет `force` или аргумента, позволяющего объявить старому artifact неподтверждённые возможности. Preflight не является встроенным production read-only режимом: старое приложение всё ещё содержит write handlers.

## Повторение

Нужен сохранённый локальный artifact с указанным build ID и fingerprint. Он не входит в публичный репозиторий. В PowerShell из корня проекта:

```powershell
$env:NODE_ENV = 'test'
$env:OT_ALLOW_ROLLBACK_DRILL = '1'
node --import tsx scripts/rollback-drill.ts 'C:/path/to/preserved/app-output'
```

`scripts/rollback-drill.ts` принимает только путь к проверяемому artifact, не принимает существующую БД в качестве назначения. Он создаёт исключительно новые файлы внутри `.data/rollback-drill-*`, проверяет реальный путь корня, использует эксклюзивное создание файлов и свои свободные loopback-порты. Секрет и пароль генерируются в памяти; email, CRM, операционные оповещения и платежи отключены. Vercel/Turso окружения отвергаются. Никакие исходные БД, `.output`, `.vercel`, сохранённый artifact или чужие процессы не изменяются и не удаляются. Частные материалы оставляются для диагностики.

Для старого runtime `OT_MIGRATIONS_DIR` направлен в отдельную копию **только `001–005`**. Его рабочий каталог тоже частный; он не получает новые SQL через root cwd. Текущие checksum сверяются до запуска; приложение читает уже расширенную схему, а не пытается откатить её.

Отдельная read-only проверка существующего локального snapshot:

```powershell
node --import tsx scripts/rollback-preflight.ts 'C:/path/to/preserved/app-output' 'C:/path/to/local/snapshot.sqlite'
```

У этого CLI exit `2` означает ожидаемый отказ в live rollback, exit `1` — ошибку входных данных/непроверенный artifact. Он использует SQLite `readonly`/`fileMustExist` и согласованную транзакцию чтения; миграции и настройки БД не меняет. Снимок чтения не даёт разрешения на более поздний deployment, когда состояние уже могло измениться.

Фактические дополнительные проверки: `npx eslint scripts/rollback-preflight.ts scripts/rollback-drill.ts` — exit 0. Общие Nuxt typecheck/build этим пакетом не запускались во время сборок основного исполнителя; две snapshot-переменные явно типизированы для общего typecheck.

Два первоначальных локальных прогона не завершились: первый не дождался холодного запуска в прежнем коротком окне, второй корректно выявил изменение auth `rateLimit`. Окно ожидания ограничено 30 секундами; исключение сузили до одного операционного счётчика, сохранив строгую проверку остальных таблиц. Успешным доказательством является только приведённый отчёт с 15/15 операциями.
