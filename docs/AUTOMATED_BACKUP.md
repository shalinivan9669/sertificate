# Автоматическая резервная копия OT Center

## Реализация и активация

`database-backup.yml` подготовлен для ежедневного запуска в GitHub Actions в 04:23 UTC и ручного `workflow_dispatch`. Он **выключен по умолчанию**: работа с БД разрешена только для `main`, когда repository variable `OT_BACKUP_ENABLED=1`. Отсутствие этой переменной или пропущенное задание не считается успешной копией. На момент подготовки место хранения и срок ещё не согласованы, секреты в GitHub не переносились, реальная автоматическая отправка архива не включена.

Это закрывает недостающий код unattended backup, но не объявляет инфраструктуру резервирования запущенной. Исходное ТЗ `spec/08_RELEASE_AND_OPERATIONS.md` требует «Автоматические зашифрованные backups БД/private files с согласованным сроком и местом хранения». Предлагаемое конкретное назначение — зашифрованные GitHub Actions artifacts этого репозитория, срок семь дней. Владелец должен согласовать это назначение/срок перед активацией. Для восстановления пароль требуется хранить отдельно от архивов и вне единственной точки отказа GitHub.

В интерфейсе Turso уже включена защита production-базы от удаления. Она не создаёт независимую резервную копию. В текущей модели private documents/BLOB находятся в БД и входят в snapshot. Если в будущем файлы будут вынесены в object storage, этот runner не станет автоматически резервировать новое хранилище: требуется отдельный экспорт и проверка его связей.

## Что делает запуск

1. Проверяет предыдущие попытки и метаданные сохранённых архивов. Сбой последней попытки не скрывается наличием старого успешного архива; отсутствующий/устаревший архив показывается отдельно.
2. Отказывается от новой загрузки при неизвестном или превышенном бюджете. Ничего не удаляет для освобождения места.
3. Устанавливает зафиксированные зависимости без доступа к DB/password secrets. Точный main revision задаётся событием GitHub; checkout не сохраняет credential для последующих Git-команд.
4. Читает согласованный snapshot удалённой БД в read transaction; не запускает миграции, приложения, worker, CRM или почту.
5. Восстанавливает snapshot в новый временный локальный файл, проверяет схему, строки, BLOB/документы, внешние ключи и физическую целостность. Измеряет actual export/restore/verification durations. Удаляет временную plaintext-БД до признания результата успешным.
6. Создаёт зашифрованный совместимый `.otb` и безопасный manifest без имён пользователей, данных таблиц, URL БД, токенов или пароля. Повторный checker проверяет AES-GCM, SHA-256 и связь manifest с аутентифицированными метаданными внутри архива. Редактирование JSON с датой/статусом не делает старую или подменённую копию успешной.
7. Загружает строго два файла: `database.otb` и `manifest.json`. Ни `.env`, ни SQLite, ни каталоги рабочей копии или временных файлов не входят в artifact. Загрузка с ошибкой не является успешным backup job.

Один runner подтверждает конкретный snapshot и восстановление; имя запланированного workflow само по себе не подтверждает выполнение по расписанию. Внешние email-уведомления в приложении остаются выключенными. Состояние попыток доступно в GitHub Actions и безопасном step summary.

## Ограничения бесплатного плана

На один encrypted archive установлен предел **8 MiB**. Для ZIP и manifest резервируется **9 MiB**. Перед запуском допускаются менее семи сохранённых backup artifacts, не более **64 MiB** backup artifacts с новой копией и не более **400 MiB** всех artifacts репозитория с новой копией. Учитываются ручные повторные запуски; список ограничен 500 записями и при неполноте проверки загрузка запрещается. Запрос превышенного размера завершается явной ошибкой, без увеличения тарифов или удаления предыдущих копий.

Это ограничение одного репозитория, а не проверка всей квоты аккаунта: GitHub учитывает storage совместно с другими репозиториями и Packages. По наблюдению 8 сентября перед добавлением backup у репозитория четыре действующих CI artifacts, всего 55 324 363 bytes. Значение является снимком, не постоянным остатком квоты. Платные изменения тарифов этот workflow не делает.

Репозиторий публичный: пользователи с доступом к его Actions могут скачать artifact. Защита archive — его шифрование и отдельно сохранённый пароль; environment не делает artifact приватным. Срок `retention-days: 7` и неизменяемость artifacts описаны в [официальном upload-artifact](https://github.com/actions/upload-artifact). [GitHub объясняет хранение и доступ к artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data). До активации следует подтвердить доступный storage всей учётной записи; запас этого репозитория не означает отсутствие расхода в других проектах.

GitHub может задерживать или пропускать scheduled jobs; в публичном неактивном репозитории расписание может отключиться. Поэтому 04:23 UTC — план запуска, **не гарантированный RPO 24 часа**. Порог metadata freshness 36 часов помогает обнаруживать пропуск при следующем наблюдении, но не является отдельным непрерывным монитором. [Ограничения schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## Настройка после согласования назначения и срока

Использовать environment `ot-center-backup` с ограничением deployment branches на `main`. Само имя environment в YAML не создаёт правила защиты; их наличие следует проверить отдельно. Перенос действующих ключей в GitHub и включение переменной выполнять только после согласования назначения резервных копий. Workflow имеет только `contents: read` и `actions: read`, не изменяет repository settings или secrets.

| Имя environment secret | Назначение |
| --- | --- |
| `OT_BACKUP_DATABASE_URL` | Явный URL согласованной source DB |
| `OT_BACKUP_DATABASE_READ_TOKEN` | Отдельный DB token только на чтение этой БД, не production write token |
| `OT_BACKUP_PASSWORD` | Случайный пароль не короче 24 символов, отдельная сохранённая владельцем копия вне artifacts |

После проверки настроек установить repository variable `OT_BACKUP_ENABLED=1`, выполнить manual run на main, подтвердить успешный `backup` job, сохранённый artifact и independent restore. Затем подтвердить следующий фактический запуск по расписанию. Для остановки удалить переменную или установить `0`; архивы не удаляются автоматически командой остановки. Правила передачи secrets в workflow приведены в [документации GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

Фактический доступ к настройкам проверен 8 сентября: браузер показывает GitHub Sign in/404 для repository environments; `gh auth status` сообщает отсутствие CLI-входа. Доступный GitHub connector не предоставляет запись secrets/административных настроек. Это отдельный доступ от уже работающего Git push. После согласования назначения для настройки environment secrets потребуется вход владельца в GitHub в браузере; пароли/ключи в чат передавать не требуется.

## Проверка и восстановление

Локально runner принимает только новую папку; родитель должен уже существовать. Секреты передавать через закрытый env file, без значений в командной строке или Git:

```sh
node --env-file=private-backup.env --import tsx scripts/backup-runner.ts --output-dir new-backup-directory
node --env-file=private-backup.env --import tsx scripts/backup-check.ts --directory new-backup-directory --max-age-hours 36
node scripts/backup-workflow-status.mjs --repository shalinivan9669/sertificate --workflow database-backup.yml --fresh-hours 36
```

Последняя команда использует `GH_TOKEN` для read-only GitHub API и проверяет метаданные, а не скачивает и расшифровывает архив. `latestUploadedBackup` не является доказательством доступности пароля или нового восстановления. При отсутствии настройки она сообщает `unconfigured`, а не `passed`. Для сверки нескольких локальных архивов повторить аргумент `--directory`; checker отдельно показывает последнюю попытку и последнюю проверенную успешную копию.

Восстановить скачанный и проверенный `.otb` в **новую** локальную БД:

```sh
node --env-file=private-backup.env --import tsx scripts/db-backup.ts restore downloaded/database.otb new-restore.sqlite
```

Не перезаписывать рабочую БД и не стирать финансовые события для отката. Функциональный план возврата приложения и восстановление наполненных учебных данных проверяются отдельно. Время локального restore не переименовывается в production RTO/RPO. Фактически выполненные проверки и оставшиеся ограничения записываются в `IMPLEMENTATION_STATUS.md`.
