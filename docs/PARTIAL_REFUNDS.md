# Confirmed partial refunds and schema013 recovery

This is internal sandbox accounting. No official payment provider, bank refund API or provider reconciliation is implemented. `OT_PAYMENT_PROVIDER=disabled` remains the production configuration. Sandbox confirmation is rejected in production, including `VERCEL_ENV=production`, and cannot send real money. Manual invoice payments are excluded from this refund operation.

The finance API requires the current finance/admin role and verified session MFA. `POST /api/v1/admin/orders/:id/refund` accepts a strict object with `reason` (10–2000 characters) and optional `amountMinor` (positive safe integer in minimal KZT units). An explicit amount requires both `currency: KZT` and an `Idempotency-Key` of 8–128 ASCII letters, digits, underscores or hyphens. The legacy reason-only full-remaining request remains valid without currency or a key. The UI sends amount, currency and a stable key. One key is scoped to the order and binds actor, reason, amount and currency. A different payload conflicts; a transport retry returns the original receipt without another confirmation or audit event.

The receipt contains `id`, `status: confirmed`, `mode: sandbox`, `orderId`, `amountMinor`, `currency`, `paidMinor`, `refundedMinor`, `refundableMinor` and `orderStatus`. Totals in a receipt describe that confirmation and remain stable on replay. Order/finance DTO totals describe current persisted state. The interface rereads current totals after confirmation. No refund reasons, actor details, provider secrets or receipt ledger are added to learner order DTOs.

Multiple confirmed receipts accumulate within the paid amount. A write transaction performs receipt insertion, order/payment transition, mandatory audit and idempotency insertion together. Partial totals produce `partially_refunded`; an exact full total produces `refunded`. The old reason-only call remains a full remaining refund; repeating it after full refund returns the final existing receipt. Positive amount validation applies to new confirmations. Zero, negative or otherwise unusual legacy amounts are preserved as historical facts by migration013, not normalized into new confirmations.

The migration appends `payment_id`, `currency` and `refunded_total_minor` columns to refunds, replacing only the old unique-one-confirmed-refund index with indexed cumulative lookups. Existing receipt identity/snapshot additions are NULL/KZT/NULL; original columns are untouched. New confirmed receipts require matching order/payment/currency and a correct cumulative total. Confirmed history cannot be changed or deleted. New ledger identity and financial states cannot be rewound by an obsolete writer. Published versions, enrollment identity, attempts, progress, documents and all their existing immutable guards remain intact. Partial refund preserves existing paid-access and credential eligibility paths, while required learning, server assessment and issuer review still apply. Full refund keeps the existing separate access/document review policy.

Analytics `refund_confirmed` remains an aggregate count of orders with a confirmed refund, deduplicated per order. The finance receipt ledger and mandatory audit retain each partial confirmation. The aggregate metric is not a count or sum of refund transactions.

## Release and recovery scope

Migration013 is a forward-only compatibility boundary for refund writers. The previous production commits a304ae5/f074385 do not implement partial receipts and are **not approved rollback targets for schema013**, even when payment dispatch is disabled. The database rejects their old confirmation INSERT shape and prevents a late succeeded event from overwriting a partial refund. Refusing an incompatible mutation is a safeguard, not proof that the old application is a usable replacement.

The earlier `scripts/release-rollback-drill.ts` remains pinned to exact a304ae5/f074385 sources and schema012. Its historical full-build/live-HTTP evidence is unchanged and does not cover schema013. `scripts/rollback-preflight.ts` retains its stricter original legacy artifact guard; migration013 is still unknown to that target and is refused. Do not delete migration013, refund receipts or their guards to make an old artifact appear compatible.

The schema013 fallback is a forward fix using a runtime built from code that implements schema013. Preserve the live database and the current archive. Restore the encrypted archive into a **new isolated empty database**, validate every table and index/trigger, and exercise current refund receipt replay and continued accounting there before selecting any replacement runtime. Retain the same production payment-disabled/email-disabled controls. An application-only change must retain the schema013 code path and checksums; never point a pre013 writer at the live database. A production artifact replacement and endpoint smoke remain a release-owner step, not a conclusion from this local source-service regression.

The reproducible bounded regression is:

```powershell
node --import tsx --test --test-name-pattern='schema013 encrypted restore' tests/business-integration.test.ts
```

It creates a private temporary database, confirms a signed synthetic sandbox payment and two partial refunds through current services, writes an actual encrypted backup file, restores into a separate empty database and compares every schema object and every row in every table. Current services replay the original receipt/key without writes, reject an obsolete state rewind, confirm only the remaining amount, and preserve every original row. The only allowed later row updates are the named order/payment status/timestamp; the only additions are one confirmed receipt and one mandatory audit. The original source database is compared again unchanged. No external service is called. Diagnostics separately measure backup, restore and current-service recovery/verification elapsed time; these are local test measurements, not a production recovery objective or proof of Vercel's rollback button.

Populated migration regressions cover schema005, 010 and 012 to 013, including historical normal/zero/negative refund rows, all prior values/checksums, foreign keys, immutability and upgrade replay. Separate business tests cover concurrent different keys, same-key races/replays, amount/currency/provider checks, atomic failure before audit commit, late signed webhooks, totals, enrollment/attempt/PDF preservation and real HTTP finance/TOTP authorization. Full release checks and current artifact staging validation are recorded by the release owner in `IMPLEMENTATION_STATUS.md`.
