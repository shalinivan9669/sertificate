# Подтверждение доставки в amoCRM: проверка ответов и повторов

Исправлена ложная фиксация доставки: раньше успешный HTTP-ответ POST примечания с пустым или неожиданным телом мог записать `crm_note_id=NULL`, `status=delivered` и событие `lead_crm_delivered`. Теперь завершение требует положительного safe-integer ID созданного примечания либо подтверждённого точного marker lookup. Неоднозначный ответ остаётся retryable с `CRM_INVALID_RESPONSE`; заявка, её внешний lead ID и состояние `note_pending` сохраняются, delivered audit/analytics не создаются.

`server/services/leads.ts` проверяет JSON и форму ответов lookup/create, положительные safe-integer ID сделок и примечаний, ранее сохранённые нулевые/отрицательные ID. Повреждённый ответ не превращается в пустой список и не порождает необработанный `.find`/`.includes` либо JSON diagnostic с данными провайдера. Корреляция сделки требует точного имени-маркера или собственного префикса `marker | `; маркер примечания должен занимать всю первую строку. Два разных ID с точным маркером требуют разбирательства, а не выбора первой записи.

Официальные API [сделок](https://www.amocrm.ru/developers/content/crm_platform/leads-api) и [примечаний](https://www.amocrm.ru/developers/content/crm_platform/events-and-notes#notes-entity-list) документируют `page`, `limit` до 250 и HAL `_links.next.href`. Оба lookup теперь обходят максимум три страницы по 250 сущностей. Продолжение разрешено только на том же origin и точном pathname, с неизменными параметрами поиска и следующим номером страницы; credentials, fragment, повтор страницы, добавленные/изменённые query-параметры запрещены. Запрос строится из исходного проверенного URL, а не пересылается напрямую по чужому href. Полная страница без `next` дополнительно проверяется следующей страницей. Неполный обход на лимите не разрешает POST создания.

Общий deadline всей последовательности и предел отдельного запроса сохранены. Максимум — восемь вызовов: по три страницы сделок/примечаний и по одному созданию, если отсутствие подтверждено. На повторе найденные по маркеру сущности используются повторно; доставленная заявка больше не обращается к transport. Схема приёма старых форм, их payload/hash, honeypot, consent и idempotency не менялись. Миграций нет.

Финальные `UPDATE status=delivered` и обязательный `lead_crm_delivered` audit теперь атомарны. Транзакция открывается только после всех HTTP-вызовов; при ошибке audit статус/ID примечания откатываются, а ранее сохранённый lead ID остаётся для безопасного повтора. Вызов без `Db` и с явным Client использует короткую `withTransaction`; переданный Transaction остаётся во владении вызывающего кода, без вложенного BEGIN или самостоятельного COMMIT. Условный UPDATE не создаёт повторный audit, если другая обработка уже зафиксировала доставку. Production worker вызывает сервис без внешней транзакции.

## Фактическая проверка

```text
node --import tsx --test --test-reporter=tap --test-timeout=30000 tests/crm-response-integrity.test.ts tests/business-integration.test.ts
npx eslint server/services/leads.ts tests/crm-response-integrity.test.ts
```

Итог после атомарного подтверждения: **41/41 passed, 0 failed/skipped, exit 0, 15,636 секунды**; 14 новых CRM-тестов и 27 существующих business-тестов. Focused ESLint — exit 0. Лог: ignored `artifacts/crm-response-integrity-tests.log`.

Новые проверки используют отдельную временную libSQL БД и синтетический transport: malformed/empty/204 успешные note responses; неправильные ID и формы lookup/create; сохранённые 0/negative ID; точные и ложные маркеры; восстановление после двух неоднозначных create responses с одним POST сделки и одним POST примечания; отсутствие delivered audit/event до подтверждения; реальный worker pending/backoff → retry → delivered; маркер на второй странице обоих lookup; чужой origin/path, изменённый query, циклическая страница и неполный обход; полная страница без `next`.

Дополнительно настоящий SQLite trigger останавливает INSERT обязательного delivery audit. Для вызовов без Db и с Client строка остаётся `note_pending`, примечание не записано как подтверждённое, delivered audit/analytics отсутствуют. Следующий вызов находит уже созданное примечание через GET и фиксирует ровно один audit/event при одном POST сделки и одном POST примечания. Во время каждого transport-вызова отдельный writer успешно открывается и откатывается, подтверждая отсутствие удерживаемой сервисом транзакции на сетевом этапе. Ещё один тест откатывает внешний Transaction после успешного `deliverLead`: ни статус, ни audit/event не переживают caller rollback; повтор в новом Transaction завершается корректно.

Первый запуск до добавления пагинации дал 34/35: искусственное прямое помещение числа вне safe-integer диапазона в SQLite ломало numeric decoder libSQL до вызова сервиса. Этот неподходящий случай хранения заменён на исторически возможные 0/negative ID; вне-диапазонные числа из ответов провайдера остаются в тестах и отклоняются до сохранения. Промежуточные запуски прошли 35/35, затем 39/39 с пагинацией; финальный с атомарным подтверждением — 41/41.

Настоящая amoCRM не вызывалась. Это сервисные/worker проверки на текущем исходном коде, не новый compiled/browser/hosted прогон. Они не подтверждают права реального аккаунта, внешний поиск при задержке индексации или exactly-once гарантию внешнего API. Неполный либо неоднозначный lookup сохраняет ошибку и требует проверки CRM оператором; нельзя расширять критерий маркера или снимать предел обхода ради формального success.
