# Corporate invoices: implemented behavior and operating contract

This capability creates a printable **Счёт на оплату** for a corporate manager's selected active, verified employees. It does not initiate transfers, contact a bank, certify a legal entity, create fiscal receipts, calculate taxes or issue an educational document. The owner confirmed the organization has the required permissions; this code performs only syntax/configuration and application authorization checks.

Enable only with `OT_INVOICE_ENABLED=1` and `OT_INVOICE_ISSUER_JSON` containing the owner's actual approved values. There are no default bank details. JSON must contain `name`, `bin` (12 digits), `address`, `bankName`, `bic` (8 or 11 uppercase characters/digits), `iban` (KZ format, 20 characters), and `paymentPurpose`. Example **shape only**, deliberately not a usable configuration:

```json
{"name":"<actual recipient>","bin":"<actual BIN>","address":"<actual address>","bankName":"<actual bank>","bic":"<actual BIC>","iban":"<actual account>","paymentPurpose":"<approved payment purpose>"}
```

With missing/invalid configuration, creation and payment confirmation return `503 INVOICES_NOT_CONFIGURED`. History and downloads remain accessible to authorized users. Apply `004-corporate-invoices.sql` through the existing explicit migration command before enabling a remote deployment. Existing migrations are unchanged.

Service contract (all functions accept the verified `AppUser` supplied by `requireUser`; finance functions also enforce current DB role and session MFA internally):

| Function | Input | Result |
| --- | --- | --- |
| `invoiceConfiguration()` | — | `{enabled,currency:'KZT',employeeLimit:100,documentFormat:'html',confirmationMode:'finance_manual_evidence'}` |
| `createInvoice(actor, organizationId, data, key)` | `{versionId,userIds:[1..100 unique IDs],buyer:{name,bin,address}}`, request idempotency key | `{invoice}` |
| `listInvoices(actor, organizationId)` | Active owner/manager membership | Configuration and `{invoices}` (latest 100) |
| `getInvoice(actor, invoiceId)` | Owner/manager of the invoice organization or finance/admin with MFA | `{invoice}` including immutable line snapshots and fulfilled enrollment/order IDs |
| `renderInvoice(actor, invoiceId)` | Same access | `{html,filename}`; serve as HTML attachment, private/no-store, noindex |
| `listFinanceInvoices(actor)` | Finance/admin with MFA | Configuration and `{invoices}` (latest 100) |
| `confirmInvoice(actor, invoiceId, data)` | `{amountMinor,currency:'KZT',reference,reason}`; finance/admin with MFA | `{invoice}` with `status:'confirmed'` |
| `cancelInvoice(actor, invoiceId, data)` | `{reason}`; organization owner/manager or admin with MFA | `{invoice}` with `status:'cancelled'` |

`invoice` includes `id`, `number`, `organizationId`, `versionId`, `status`, `amountMinor`, `currency`, `snapshot`, `createdAt`, `confirmedAt`, `confirmation`, `cancelledAt`, `cancellationReason`, and `lines`. Snapshot includes the issuer/buyer requisites, program title/version, quantity and unit amount. Lines contain `id`, `userId`, `learnerName`, `email`, `programTitle`, `versionId`, `amountMinor`, and nullable `orderId`/`enrollmentId`. List results omit detailed lines (empty array); retrieve details to view participants.

Creation reads price only from the pinned, published paid version. `ProgramData.billingBasis` is `learner` by default (including older immutable versions) or explicitly `organization`. Per-learner totals multiply unit price by participant count; organization totals charge the fixed unit price once for the selected organization, regardless of whether 1 or 100 employees are selected. The caller cannot supply price, billing basis, currency, quantities or status on the invoice request. Every participant must still be an active verified member of the active organization. Existing active/completed/suspended assignments and succeeded corporate orders block duplicate purchases. A unique reservation per organization/user/version prevents overlapping unpaid invoices. Existing `pending_access` seats can be paid and activated; creation itself grants no access. Cancellation releases reservations while preserving immutable history.

Migration `005-invoice-allocations.sql` adds immutable per-seat integer allocations without rewriting migration 004 or existing line snapshots. For an organization fee, quotient plus remainder allocations sum exactly to the invoice total; zero allocations are permitted when the group fee has fewer minor units than seats. A 125,003-minor-unit fee for 100 employees allocates 1,251 to three orders and 1,250 to 97 orders. All linked orders/payments together still total 125,003. `snapshot.quantity` is participant count; `snapshot.billingBasis` explains the fixed fee, and print view displays one organization service with participant count in its description. DTO `line.amountMinor` is its exact allocation. Existing per-learner lines with no allocation retain their original amount. Organization-priced versions cannot use individual checkout.

Confirmation is a reasoned **manual record of payment evidence**. The financial employee must check the actual bank statement outside this application and enter the exact total, KZT currency, transfer reference and reason. The code does not claim to have verified the bank. A normalized transfer reference cannot confirm another invoice. A repeat with identical evidence returns the committed result; conflicting evidence is rejected. All selected employees are rechecked inside the same transaction; one revoked member prevents partial fulfillment. The transaction creates/reuses assignments, creates a succeeded order and `manual_invoice` payment per seat, records line fulfillment, marks the invoice confirmed, audits the actor and queues internal notifications. Remote delivery remains governed by the existing separate flags. Sandbox refunds must not process `manual_invoice` orders.

Server conditions for lessons, instructor-confirmed practice, timed exams and actual approved document templates remain mandatory. A paid invoice does not create progress, a passing attempt or a certificate. Download is print-ready escaped HTML with no executable scripts, external fonts, fake seal or signature; browser printing can produce a PDF. It is explicitly labelled as an invoice, not a fiscal or educational document.

Actual checks run: `node --import tsx --test --test-reporter=tap tests/core-domain.test.ts tests/invoices.test.ts` — **29/29 pass**, including **11 invoice tests**, using real migrated isolated local libSQL databases. Covered disabled configuration, organization ACL/stale replay, fixed server price, 100-seat limit, forbidden extra fields, immutable snapshots/line append/delete, escaped HTML, concurrent idempotency, overlap/cancellation, real current finance role/MFA, wrong amount/currency, revoked-member atomic rollback, pending-seat reuse, exact payment replay, duplicate bank reference, unchanged academic prerequisites and bounded SQL. The 100-seat case checks both per-learner and fixed organization fees, exact remainder allocation and print quantity; another test confirms a one-minor-unit fee across three covered seats. A 100-person confirmation uses at most 30 SQL statements; creation at most 20, independent of participant count. No external bank/database or real payment record was used.
