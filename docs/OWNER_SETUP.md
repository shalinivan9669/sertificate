# Первый владелец при выключенной почте

`scripts/owner-setup.ts` — отдельная доверенная операторская команда для начальной настройки. Она не доступна через HTTP и не меняет проверки входа, ролей или MFA в приложении. Использовать её можно только после явного подтверждения владельцем точного уже зарегистрированного email и ручной активации этого аккаунта. Доступ оператора к Turso сам по себе не является таким подтверждением.

Подготовка команды не означает, что она применена. В текущем подэтапе применения нет: ожидается email владельца. Скрипт не запускался и не проходил тесты по просьбе владельца остановить проверки.

## Предварительный просмотр

В защищённом окружении оператора уже должны быть `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN`. Не передавайте токен аргументом команды или сообщением в чат. Команда открывает явно заданную удалённую БД, без локального fallback, миграций и автоматического наполнения.

```powershell
node --import tsx scripts/owner-setup.ts --email 'owner@example.com' --reason 'Владелец явно подтвердил этот аккаунт и разовую ручную активацию'
```

По умолчанию выполняется только read transaction: проверяется отсутствие администратора, наличие точного пользователя с одним password credential и количество его сессий. Вывод не содержит пароля, email, TOTP, cookie, банков вопросов или реквизитов БД. Audit в режиме просмотра не создаётся.

Необязательный `--draft 'C:/private/program-import-private.ru.json'` добавляет предварительный просмотр импортного пакета. Файл ограничен 500 КБ и проходит те же структурную и содержательную валидации, что редактор. Дата проверки сбрасывается. Программа должна быть активной и ещё не иметь ни одной версии; иначе импорт выполняют позднее через редактор. В консоли показываются только program ID, SHA256 файла и количества уроков/вопросов.

## Применение после подтверждения владельца

К тем же аргументам добавляют **оба** флага `--apply --activate-owner`. Одного `--apply` недостаточно. Нельзя подставлять email из догадки, тестовой fixture или другого аккаунта. Отказ из-за существующего администратора не является поводом удалять его или обходить эту границу.

В одной write transaction повторяются все условия, затем:

1. Выбранный зарегистрированный аккаунт активируется вручную и получает роль первого администратора. Пароль не задаётся и не меняется.
2. Отзываются прежние сессии только этого пользователя. Имеющиеся TOTP-настройки сохраняются; сессии и отметки прохождения MFA не создаются.
3. В audit отдельно записываются ручная активация по подтверждению владельца и назначение первого администратора.
4. Если указан пакет, создаётся отдельная закрытая версия `draft`, автором которой фиксируется владелец. Рецензия, публикация, зачисления, экзамены и документы не создаются.

Любой конфликт откатывает все изменения этой транзакции. Команда не повторяет запись при неопределённом результате commit: сначала нужно прочитать текущий audit и данные. Повторный запуск после успешной настройки остановится из-за существующего администратора.

Система использует поле Better Auth `emailVerified` как условие допуска к аккаунту, поэтому ручная активация устанавливает его. **Это не доказательство проверки почтового ящика через письмо:** основанием служит явно подтверждённая владельцем операторская активация, что отражается в audit. Письма остаются выключенными, а обычная регистрация других пользователей и восстановление пароля не превращаются в завершённые почтовые процессы.

После применения владелец входит на `/auth/login` со своим прежним паролем, настраивает TOTP в `/cabinet/security` либо подтверждает уже настроенный второй фактор и открывает `/admin/programs`. Коды и пароль в чат не передают. Для публикации импортированной версии по-прежнему нужен отдельный рецензент; владелец, записанный автором, не может утвердить её сам. Часы и правила программы также должны быть утверждены до рецензии.
